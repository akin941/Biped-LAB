### 1.5 Actuators (VERIFIED)
- The XML has 14 `<position class="chosen_actuator">` actuators (`robot_walk.xml:412-425`).
- Class `chosen_actuator` (`joints_properties.xml:23-31` = `robot_walk.xml:44-46`):
  - joint `damping=0.053`, `frictionloss=0.0048`, `armature=0.0018`
  - `<position kp="0.55" kv="0.0" forcerange="-0.96 0.96" ctrlrange="-10 10"/>`
- Alternative classes are also defined: `perfect_actuator` (kp 10, kv 0.1, ±20), `chosen_actuator_old` (kp 0.52, ±0.91), `chosen_actuator_new` (kp 0.386, ±0.67) and `chosen_actuator_antoine` (kp 0.43, ±0.75) (`joints_properties.xml:2-22`).
- **Training does not use the XML PD.** All tasks use the BAM M6 XL330 actuator `FrictionDRBamActuatorCfg` on joints matching `^(?!passive_).*` (`microduck_constants.py:163-176`):
  - `kp_fw=200.0`
  - `vin_range=(6.5, 8.2)` V
  - `vin_drop_gain_range=(0.0, 0.2)`
  - `vin_min=6.0`
  - `delay_min_lag=3`, `delay_max_lag=6`
- BAM converts the position actuators into torque motors with `forcerange = ±vin·kt/R`. It zeroes joint damping and frictionloss because BAM writes the friction budget itself every step, and it uses a stiff friction solref `(-5e4, -2e2)`. This conversion is VERIFIED as mirrored on CPU in `scripts/infer_policy.py:59-105` and locked by `tests/test_infer_policy_bam.py:56-75`.
- The kt and R values live inside the BAM package. UNVERIFIED: not in this repo.

## 12. Gaps, risks, CUDA-only assumptions, Apple Silicon blockers
1. **Training is CUDA-only by design.** VERIFIED claims: `README.md:24`; `pyproject.toml:92-96` (`select_gpus()` IndexError without CUDA torch). MuJoCo-Warp kernels target CUDA.
   - warp-lang 1.12.0 ships a macOS arm64 wheel (`uv.lock:2145`), but Warp on macOS is CPU-only (ASSUMPTION, external knowledge).
   - mjlab's GPU selection would fail without CUDA (VERIFIED as stated).
   - **Apple Silicon cannot train** with this stack; nothing in the repo targets MPS. Even if mjlab accepted a CPU device, a CPU warp backend would be impractically slow at 4096 envs (ASSUMPTION).
2. **Export needs the mjlab env.** `export.py` builds a `ManagerBasedRlEnv` (MuJoCo-Warp) even on CPU (`export.py:75,214`). On a Mac this is UNVERIFIED and likely blocked by item 1. Mitigations: export on the GPU host or HF Jobs, or write a standalone exporter (torch actor plus `EmpiricalNormalization` → `torch.onnx.export`).
3. **CPU inference path is the Mac-friendly part.** `scripts/infer_policy.py` needs only `mujoco`, `onnxruntime` (macOS ≥14 wheel), `numpy` and BAM (git; pure Python per its locked deps). Caveats:
   - (a) `mujoco.viewer.launch_passive` requires `mjpython` on macOS (ASSUMPTION, external).
   - (b) There is no headless mode, and it reads keys from the TTY.
   - (c) It defaults to `robot_groundcontact.xml`, not the walk model.
   - (d) The quickstart command omits `--new-cmd-obs`, so a 61-D policy gets a 51-D obs (VERIFIED, `README.md:45` vs `infer_policy.py:1196-1199`).
   - (e) No obs noise, IMU misalignment, encoder bias or obs delays are applied, but the BAM actuator matches training.
4. **The mjlab source is not vendored.** Reward base weights (foot_clearance, foot_swing_height), terminations, episode length, decimation, the ONNX opset and IO names, the metadata keys and the default `num_envs` all come from `mjlab==1.3.0` and were not checked. Pin mjlab 1.3.0 and read its `tasks/velocity/velocity_env_cfg.py` and `rl/exporter_utils.py` before reimplementing.
5. **BAM comes from a feature branch** (`mjlab_frictionloss`, commit `62bd8ce`), not a release (`pyproject.toml:87-89`). The branch can disappear; vendor it or pin by SHA. It needs GitHub network access at install, and its `zmq==0.0.0` dependency is broken and dropped by an override (`pyproject.toml:78-82`).
6. **Python is pinned to 3.12 only** (BAM <3.13). Torch is pinned at 2.9.1 deliberately (`pyproject.toml:29-37`).
7. **The obs contract is fixed at 61 → 14** and shared by all policies (hot-swap). The runtime daemon refuses other shapes (`publish/manifest.py:23-27`).
